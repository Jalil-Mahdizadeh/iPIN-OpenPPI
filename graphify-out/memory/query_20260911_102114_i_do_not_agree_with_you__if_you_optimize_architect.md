# Q: I do not agree with you. If you optimize architecture/hyperparameters exclusively on the development panel, freeze the final model, and then evaluate that final model on the test set, that is a standard and defensible train/dev/test workflow. We only apply the optimized model if it shows improvement on the development panel over the base model. We do not need to develop another unseen test set.

## Answer

Expanded via graph vocabulary: development selection protected test evaluation protocol freeze. The user correctly distinguishes development-only model selection from repeated test-driven tuning. scikit-learn official cross-validation guidance https://scikit-learn.org/stable/modules/cross_validation.html specifies training on training data, selecting hyperparameters on validation data, and final evaluation on held-out test data. Prior baseline evaluation does not automatically make every subsequent benchmark comparison invalid; Mania et al. NeurIPS 2019 https://papers.neurips.cc/paper_files/paper/2019/hash/48237d9f2dea8c74c2a72126cf63d933-Abstract.html gives theoretical/empirical conditions mitigating overuse, not a guarantee for this PPI benchmark. Dwork/Hardt https://research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/ supports the retained warning that test feedback can guide analysis even without training on test labels. Recommend a bounded follow-up using the existing split, subject to explicit prospective protocol authorization: freeze search budget, hypotheses, primary C3 metric, development improvement gate, seed aggregation and stopping before training; train/preprocess only with training inputs; make all architecture/hyperparameter/checkpoint decisions on development evidence without targeting known test scores or subgroups; nominate one final winner only if a prespecified robust development comparison beats the baseline; freeze all predictions and evaluate the fixed winner on the existing test once, compare to the unchanged frozen baseline using paired component-aware uncertainty; publish positive, null or adverse outcomes and do not initiate another optimization round from test feedback. Preserve the original model/result/custody records. Disclose that the baseline test results had already been inspected before this follow-up, and do not describe the second comparison as independent replication or a never-seen test. An existing test result that actually guides model/search choices violates the stronger development-only premise; a dev improvement gate alone is not a proof against such adaptivity. A new panel would strengthen independent confirmation and external validity, but need not be an absolute prerequisite for this carefully scoped follow-up benchmark claim. Current DEC-0051 L31-36 and PROTECTED_FINAL_TEST_v1 L94-114 prohibit repeat access/ledger resets, so any future execution needs a new authorized prospective protocol preserving history, not edits to the frozen original or bypassing the ledger. This turn revises methodological advice only: no model fitting, test access, ledger change, protocol change, commit or push.

## Outcome

- Signal: corrected
- Correction: The earlier statement that a genuinely fresh test panel is an absolute prerequisite for any defensible follow-up model comparison was too categorical. A previously evaluated benchmark can support a transparently documented, development-selected follow-up comparison. This is not a new never-seen holdout or independent replication, and prior feedback/adaptivity risks do not disappear merely because fitting and the final promotion gate use development labels. Existing one-shot custody/protocol restrictions are project commitments requiring prospective explicit user-authorized amendment, not an unchangeable statistical law; no amendment or rerun is authorized by this discussion alone.
